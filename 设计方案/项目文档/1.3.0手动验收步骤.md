# 1.3.0 补充手动验收步骤

> 本文记录补充验收步骤及结果，不代表所有项目都必须纳入 1.3.0。普通母体自然生成状态保存、低入口生存通行与战斗、九种变体宝箱 GUI 检查均已在 `1.2.0` 打包发布前通过；本页步骤保留供查阅或复测，不再是待测项。具体记录见下表；没有留档的截图、锚点或逐箱物品清单不作补造。

## 开始前

1. 使用独立 Forge 1.20.1 测试实例和正式 `1.2.0` 模组 JAR；不要在日常游戏实例里做这组测试。
2. 新建只用于 QA 的测试世界，开启作弊，保留默认主世界和正常难度。需要重新开始某项测试时，新建 QA 世界或换到至少相距 600 格的空区，别在玩家存档中试。
3. 自然生成测试要用未探索的新区域。定位扫描会逐步加载候选区块；如果搜索失败，保留最后的诊断消息，不要在同一区域反复扫描。
4. 把坐标、命令输出、截图和结果记入本页末尾的记录表。出现失败时先停止后续步骤并保留世界，便于复现。
5. 不使用 `/kill`、直接改 NBT 或破坏结构来替代真实战斗；只有“战利品表静态核对”可用资源文件作为证据。

## A. 自然生成母体的状态保存

**状态：**发布前五项检查已通过（用户确认）；当时未留存截图、QA 存档名和锚点。

**目标：**检查自然生成的守卫室在区块卸载和正常保存退出后，监守者、门与奖励状态不会错乱。

1. 在新建 QA 世界传送到较远的新区域，执行：

   ```mcfunction
   /starrail ruin locate ordinary
   ```

2. 按命令给出的传送坐标前往遗迹，等待区块完全加载。执行 `/starrail ruin guard_status`，记录锚点、守卫 UUID、奖励解锁状态和门格数。预期是守卫在场、奖励未解锁、门格 `0/25`。
3. 离开遗迹至少 256 格并等待 30 秒，再返回同一锚点。重新查询状态并观察一分钟。预期是原 UUID 对应的守卫仍在，不会多刷一只；奖励仍锁定，门格仍为 `0/25`。
4. 用“保存并退出”正常关闭世界，再重新进入同一个 QA 世界，传送回记录的锚点附近并等待加载。再次查询状态。预期仍是同一 UUID、单只守卫、奖励锁定、门格 `0/25`。
5. 切换到生存模式，按正常战斗击败守卫。预期是出现解锁提示，状态变为已击败/奖励已解锁，门格达到 `25/25`，铁栅门打开。
6. 正常保存退出并重新进入。返回原锚点，确认守卫没有重生、门保持打开、解锁状态不回退。打开箱子并记录物品；取走物品后再保存退出、重进，确认箱子不会重新生成一份战利品。

**通过条件：**击败前后状态都能保存；守卫没有重复生成；击败后不会重新锁门或重复发奖。若只完成了单人世界退出重进，专用服务端重启这一项另记为“未测”，不能把两者混为一项。

## B. 低入口的生存通行与战斗

**状态：**发布前已通过（用户确认）。

**目标：**实际确认玩家能进退，原版监守者不会被入口、台阶或遗迹装饰卡住。

1. 在另一个 QA 世界空区放置普通母体样本。执行 `/difficulty normal`，再执行：

   ```mcfunction
   /starrail ruin place ordinary ~ 200 ~
   ```

   等待进度到 `100%`，记录命令报告的锚点。若间距检查拒绝放置，换一处距其他遗迹更远的空区，不要加 `overwrite`。
2. 准备适合测试的普通生存装备、食物和恢复物品；切到生存模式，从主殿正面入口进入，再原路撤出。观察玩家是否会被门洞、台阶或装饰卡住。
3. 接近并触发监守者，观察它能否在战斗区内正常移动、转向和追击；沿入口撤退，再从入口返回。保留原版难度与行为，不使用药水或命令削弱/强化监守者来判定结构通行。
4. 记录监守者是否被栏杆、楼梯或低顶困住，是否能威胁入口附近的玩家，以及玩家是否有清楚可走的进退路线。不要为了“通过”而改造遗迹。
5. 若测试角色死亡、监守者被卡住或路径不清，记录具体坐标、方块位置、难度和截图，判为失败并保留该 QA 世界。

**通过条件：**玩家可以正常进出；监守者在原版行为下能参与战斗，没有被结构困死；入口附近的交战和撤退都可实际完成。是否要把入口改成更宽或更高，留待看到失败证据后再设计。

## C. 九种命途变体战利品 GUI 抽查（建议项）

**状态：**九种变体均已通过实际开箱检查（发布前由助手测试，用户确认）；本记录未保存逐箱截图和完整物品清单。

**目标：**在实际打开的箱子中核对各变体奖励内容和试炼凭证命途。

本项会放置多座大型遗迹，QA 存档会增长；只在接受该存档暂时变大的前提下做。不要用同一锚点连续覆盖不同命途：守卫完成状态按锚点保存，覆盖蓝图不会自动重置旧守卫状态。

1. 在 QA 世界开启作弊，设为普通难度。逐个使用下表的命途 ID；每座之间至少相距 600 格，并等待该座放置完成后再执行下一条：

   | 命途 | 命令中的 ID |
   | --- | --- |
   | 存护 | `preservation` |
   | 毁灭 | `destruction` |
   | 巡猎 | `hunt` |
   | 智识 | `erudition` |
   | 同谐 | `harmony` |
   | 虚无 | `nihility` |
   | 丰饶 | `abundance` |
   | 记忆 | `remembrance` |
   | 欢愉 | `elation` |

   每座使用命令格式 `/starrail ruin place <ID> <X> 200 <Z>`。选择空区；如果收到 400 格间距拒绝提示，换到更远位置。不要在正式存档运行。
2. 每座先执行 `/starrail ruin guard_status`，确认锚点与该次放置位置对应、奖励未解锁、门格 `0/25`。然后在生存模式中击败这座遗迹自己的监守者。
3. 等门打开后打开箱子，记录奖励物品，以及试炼凭证悬浮提示中的命途名称/`Path`。凭证必须与该座 ID 对应；随机材料、数量和光锥不要求九箱完全相同。
4. 每座只开一次并记录结果。若同一箱开过后再次进入仍看到空箱，这是预期行为，不作为缺少战利品的证据。

**通过条件：**九座各自的箱子都能在守卫击败后打开；凭证命途与该座一致；没有空箱、错误命途凭证或战利品重复绑定。单纯查看 JSON/NBT 只能证明绑定关系，不能代替 GUI 内容抽查。

## D. 存档兼容性验收策略

同属 Minecraft `1.20.1` 的 Mod 版本更新（例如 `1.1.0` 升至 `1.2.0`）不单独安排旧存档迁移验收，也不作为当前版本的待测项。这是项目的测试范围选择，不代表曾经完成过这类迁移测试。

只有计划更换 Minecraft 基础版本时，才新增跨版本存档兼容测试，例如从 `1.20.1` 迁移至 `1.21.1` 或 `26.1`。届时使用可确认来源的旧版存档副本，保留原档不动；在目标版本检查玩家数据、物品、旧区块与遗迹，并保存退出后重进复核。没有可信旧档样本时记为“未测”，不在真实存档上试验，也不伪造兼容结论。

## E. 多人支持范围（先做决定，不在本轮盲测）

发布归档没有承诺多人连接。先在 1.3.0 范围里明确“支持多人”或“暂不承诺多人”；选定支持后，再另写双客户端专用服务端步骤，检查世界共享的守卫进度是否一致，以及每位玩家各自的当前命途、待寻迹目标和凭证启动流程是否互相串线。没有第二个客户端时记为“未测”，不能只凭单人世界结果判通过。
